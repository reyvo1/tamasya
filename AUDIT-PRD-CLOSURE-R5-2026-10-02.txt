ROOT CAUSE
R4 correctly replaced mysqladmin process-liveness with authenticated SQL readiness, but it then intentionally reused the application runtime account as schema owner. Canonical schema contains triggers. Under binary logging MySQL correctly prevents a non-administrative runtime account from creating those trigger objects. The problem is authority separation, not readiness, not the trigger definition, and not hotel business logic.

This also conflicted with existing production provisioning semantics in deploy/provision_property.php, which already instruct DBA schema import and grants runtime only SELECT/INSERT/UPDATE/DELETE on the property database.

R5 ROOT FIX
1. Added tests/uat_prd/mysql-bootstrap-runtime-boundary.sh as the single PRD schema/runtime authority harness.
2. Disposable MySQL fixtures no longer use MYSQL_USER/MYSQL_PASSWORD auto-provisioning, avoiding Docker's broad database grant for the app identity.
3. Fresh schema and triggers are imported only through disposable migration/DBA authority.
4. Runtime PMS identity is created only after schema import with SELECT,INSERT,UPDATE,DELETE.
5. HQ runtime identity is created only after HQ schema import with SELECT,INSERT,UPDATE.
6. SHOW GRANTS is inspected for forbidden CREATE/ALTER/DROP/TRIGGER/GRANT OPTION/SUPER/ALL PRIVILEGES.
7. Runtime CREATE TABLE is behaviorally required to fail.
8. Runtime SET GLOBAL log_bin_trust_function_creators is behaviorally required to fail.
9. Wrong runtime password is still required to fail.
10. Existing authenticated TCP SELECT readiness contract is retained for migration and runtime identities.
11. SaaS canonical table/trigger count checks are retained: 113 tables, 5 triggers.
12. HQ external adapters use the same authority split.
13. Deployment runbook now states migration/DBA credentials must not be mounted into PHP-FPM/worker/realtime/HQ runtime; shared-hosting one-user limitation is documented as a platform exception.
14. Added PRD database-authority regression and rerun it after runtime simulation.
