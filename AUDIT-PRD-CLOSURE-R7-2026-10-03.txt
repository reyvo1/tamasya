ROOT CAUSE A — INVALID SAAS RUNTIME FIXTURE, NOT RANDOM PHP FAILURE
api.php intentionally requires APP_TIMEZONE plus immutable TAMASYA property identity (ID/code/name) before normal API startup. R6 tests/uat_prd/run_saas_runtime_smoke.sh supplied property ID but omitted APP_TIMEZONE, TAMASYA_PROPERTY_CODE and TAMASYA_PROPERTY_NAME. The test therefore started an invalid deployment fixture and then probed it as if it were production-valid. R7 fixes the fixture contract and captures the last HTTP body plus api/api2/web logs on readiness failure instead of hiding the error behind curl -f.

ROOT CAUSE B — TRIGGER INTEGRITY CROSSED AUTHORITY BOUNDARIES
R5/R6 correctly separated migration/DBA authority from DML-only runtime authority. MySQL hides information_schema.TRIGGERS from the least-privilege runtime. Runtime startup still needs proof that canonical triggers exist, but granting TRIGGER/DDL to the runtime merely to inspect metadata would destroy least privilege.

R7 implements an explicit release attestation chain:
1. migration/DBA authority imports the canonical schema;
2. privileged verifier proves exact canonical tables and trigger signatures;
3. only after that PASS, migration authority writes current_release, patch_level, exact SHA-256(database_setup.sql) and migration_run_id into schema_release_state;
4. runtime remains DML-only;
5. if runtime can directly see trigger metadata, direct metadata remains authoritative;
6. if metadata is deliberately hidden by least privilege, runtime accepts the delegated proof only when the stored canonical checksum exactly matches its own database_setup.sql and migration_run_id is present;
7. stale/missing checksum, unknown visibility, or directly visible missing trigger remains fail-closed.

Production provisioning now generates release_attestation.sql as a separate reviewed DBA step. first_install/finalizer/configurator persist canonical source provenance where applicable. Strict database_verify remains the migration/maintenance authority gate; it is not weakened.

ROOT CAUSE C — REAL POS MIDNIGHT ROLLOVER BUG
The mobile browser test crossed the hotel business date while the POS page stayed open. The sale was created on 2026-10-03, but the sales filter still held the bootstrap value 2026-10-02. This is a real application-state bug, not test flakiness.

R7 adds a dedicated server-authoritative business-date policy. Automatic sales periods follow businessDate/businessMonthStart on every bootstrap/focus refresh and when opening the Sales view, including midnight/month rollover. An operator-selected custom historical period remains untouched. The POS policy and client have explicit cache-busted URLs and SW entries, preventing stale deployed JavaScript from preserving the old behavior.
