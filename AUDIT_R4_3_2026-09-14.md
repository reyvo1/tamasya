# Audit kode dan perbaikan R4.3 — 14 September 2026

## Keputusan rilis

**Perbaikan kode selesai untuk tujuh kelompok masalah yang dikonfirmasi. Paket ini adalah kandidat staging, belum persetujuan go-live.**

Audit dilakukan terhadap ZIP R4.2 yang diberikan pengguna. Seluruh 101 PHP dan 57 JavaScript/MJS asli menjalani pemeriksaan sintaks. Penelusuran logika difokuskan pada batas transaksi, POS, reservasi, autentikasi/izin, Telegram, cache offline, dan retry permintaan; backup, sinkronisasi, setup, dan konfigurasi turut ditinjau secara statis. Ini bukan bukti bahwa setiap cabang seluruh fungsi sudah diuji.

Tidak ada koneksi ke database hotel, pengiriman Telegram, perubahan server produksi, atau deployment. Dokumen audit lama di paket merupakan riwayat; klaim pengujian di dalamnya tidak dihitung sebagai hasil audit ini.

## Masalah yang diperbaiki

| ID | Prioritas | Temuan dan dampak | Perbaikan |
|---|---|---|---|
| A1 | Tinggi | `080_telegram_webhook.php` memanggil `telegramPlainText()` sebagai fungsi global pada konfirmasi insiden, padahal formatter adalah closure `$telegramPlainText`. Error terjadi sesudah commit, sehingga insiden tersimpan tetapi balasan menyatakan gagal. | Kedua pemanggilan memakai closure yang sudah didefinisikan. |
| A2 | Tinggi | Diskon POS dibulatkan terpisah untuk setiap item; contoh 100 item masing-masing 1,00 dengan diskon 0,50 menghasilkan alokasi 0,99. Transaksi valid dapat ditolak oleh pemeriksaan keseimbangan. | Pembagian dalam satuan sen dengan distribusi sisa pembulatan; jumlah bagian sama persis dengan diskon dan tidak melebihi harga item. |
| A3 | Tinggi | Pemeriksaan shift POS tidak mengunci baris shift. Jika kebijakan umum `require_open_shift_for_sale` dimatikan, pengaitan transaksi berikutnya juga tidak mengunci shift; penutupan shift dapat berlomba dengan penjualan. | Pemeriksaan awal POS memakai `FOR UPDATE` ketika transaksi database aktif, berlaku pula untuk void langsung. |
| A4 | Tinggi | Nama cache service worker sama untuk semua subfolder pada satu origin; aktivasi satu instalasi dapat menghapus atau membaca cache instalasi lain. | Namespace cache memakai path scope, pencarian cache dibatasi ke cache instalasi sendiri, aktivasi hanya membersihkan namespace sendiri. |
| A5 | Tinggi | Semua navigasi selain beberapa halaman khusus dianggap shell aplikasi. Halaman PHP, website publik, URL upload, atau halaman file yang salah dapat menggantikan cache `index.html` atau menerima shell saat offline. | Bypass PHP, upload, website publik dan file navigasi yang tidak dikenal; cache aset runtime dibatasi pada aset aplikasi. |
| A6 | Sedang | HTTP 202 dianggap sukses oleh pelindung submit ganda sehingga retry sah diblokir 409. HTTP 200 dengan JSON `success:false` juga mengaktifkan pemblokiran sukses. | Hanya hasil terminal yang berhasil mengaktifkan pelindung; retry 202/503 tetap membawa operation ID sebelumnya. |
| A7 | Tinggi | `!empty()` menganggap izin teks `"false"` sebagai aktif. Bentuk grup izin salah dapat memicu TypeError; JSON izin rusak dapat jatuh ke izin bawaan role. | Pembacaan override izin eksplisit dan terpusat. Boolean/angka 0–1 serta teks true/false dibaca aman; bentuk rusak ditolak. Izin yang tidak ditentukan tetap memakai fallback role. |

Perubahan pendukung: versi URL aset guard/service worker diperbarui, build ID dibedakan, peta fungsi dilengkapi, dan checksum paket dibuat ulang. Identitas rilis/skema database dipertahankan karena tidak ada perubahan skema.

## Bukti pengujian

- PHP CLI 8.4.24 dan Node.js 22.23.1 pada Windows.
- 44 pemeriksaan regresi PHP dan 11 pemeriksaan JavaScript: **55 lolos, 0 gagal**.
- Pengujian PHP mencakup 1.000 keranjang diskon deterministik, pembulatan kecil, kunci shift melalui test double, formatter balasan insiden, bentuk izin, kalender, serta interval reservasi berdampingan/bertumpang tindih.
- Pengujian JavaScript menjalankan kode guard/service worker dalam konteks VM dengan mock Fetch/Cache. Mencakup isolasi subfolder, bypass navigasi, retry 202/503, serta pemblokiran submit setelah sukses.
- Suite yang sama terhadap kode asli: **37 lolos, 18 gagal**. Sesudah perbaikan: **55 lolos, 0 gagal**. Jumlah kegagalan adalah kasus uji, bukan jumlah bug terpisah.
- Pemeriksaan sintaks seluruh PHP/JS/MJS, parsing JSON, inline JavaScript HTML, referensi aset HTML/precache/import literal JS, dan peta lokasi modul. Detail per file ada di `verification.json` dalam bukti audit terpisah.
- Kedua script PowerShell lolos parser; kedua wrapper shell ditinjau statis. Daemon tidak dijalankan.

Jalankan kembali dari root paket:

```text
php tests/regression.php
node tests/regression.mjs
```

Tests membutuhkan PHP 8.2+ dan Node 22 untuk harness JavaScript. Direktori tests diblokir oleh `.htaccess`, dan test PHP menolak akses web. Test tidak membutuhkan database dan tidak menghubungi layanan eksternal.

## Batasan dan temuan yang belum diselesaikan

1. **SQL/database belum dieksekusi.** Tidak tersedia instance MySQL/MariaDB staging beserta konfigurasi hotel. Import skema, trigger, foreign key, perubahan saldo/folio, rekonsiliasi jurnal, rollback, dan deadlock nyata belum dibuktikan. Test double kunci shift memverifikasi permintaan lock, bukan simulasi server database paralel.
2. **Migrasi legacy RC4.4 masih memiliki referensi fungsi lama yang tidak tersedia**, yaitu `reconcileRoomTaxMetadata` dan `reconcileBookingTaxMetadataBatch` di `api/support/080_schema_alignment.php`. File legacy ini tidak dimuat oleh bootstrap API fresh yang ditinjau. Tidak dibuat fungsi pajak pengganti secara spekulatif. Jika ada launcher/migrator tambahan di server yang memuatnya, jalur upgrade tersebut harus diaudit dan diperbaiki sebelum digunakan. Paket ini tidak menyatakan upgrade database lama sudah aman.
3. **Domain bawaan masih mengikuti berkas pengguna:** `app.nolink.my.id` dan `tamasya.nolink.my.id` muncul pada runtime website publik dan alat konfigurasi. Tidak diganti tanpa informasi domain deployment. Periksa bahwa itu benar-benar tujuan milik hotel; generator legacy dapat memakai default tersebut jika URL tidak diisi.
4. Belum ada pengujian browser nyata, Apache/LiteSpeed `.htaccess`, mode offline nyata, Telegram/2FA, email, smartlock, upload identitas, sinkronisasi dua node, maupun restore backup.
5. Uji hanya memakai PHP 8.4.24; kompatibilitas runtime PHP lain perlu dijalankan di lingkungan target. Tidak ada audit CVE menyeluruh terhadap bundle vendor atau dependensi sistem.
6. Cache lama yang memakai namespace global sengaja tidak dihapus otomatis karena dapat sedang dipakai instalasi subfolder lain. Cache baru tidak membacanya. Penghapusan cache lama dilakukan setelah semua instalasi satu origin selesai diperbarui.

## Validasi staging sebelum produksi

Gunakan server dan database staging terisolasi. Untuk instalasi baru, import `database_setup.sql` hanya ke database kosong. Untuk instalasi yang sudah berisi data, jangan import baseline fresh; siapkan jalur upgrade sesuai skema yang benar dan backup teruji.

1. Atur ENV/identity/domain hotel, jalankan pemeriksaan preflight yang tersedia, selesaikan setup hingga READY, dan cek build ID R4.3. Pertahankan secret serta berkas upload milik instalasi yang sudah ada.
2. Uji login, 2FA, pembatasan role/capability, sesi kedaluwarsa, serta role yang memang tidak boleh mengakses identitas tamu/keuangan.
3. Uji reservasi bentrok oleh dua petugas, check-in, perpanjangan, pindah kamar, pembayaran split, refund, checkout, maintenance dan inspeksi housekeeping. Saldo booking/jurnal harus tetap seimbang.
4. Uji POS 100 item dengan diskon kecil, stok tidak cukup, void, charge kamar, serta penjualan bersamaan dengan penutupan shift pada pengaturan shift wajib aktif maupun nonaktif.
5. Putuskan koneksi sesudah submit. Retry tidak boleh membuat transaksi kedua. Uji dua subfolder pada origin sama dan pastikan shell/cache tidak tertukar.
6. Kirim insiden Telegram dan pastikan satu insiden tercatat dengan balasan sukses. Uji kegagalan layanan komunikasi tanpa mengulang mutasi bisnis yang sudah commit.
7. Jalankan backup lalu restore ke database terpisah; cocokkan tabel, jumlah data dan saldo. Uji sinkronisasi/putus koneksi/failover jika dua node digunakan.

Go-live dilakukan setelah hasil staging tersebut memenuhi kebutuhan hotel. Tidak ada klaim bebas bug atau aman produksi hanya berdasarkan lint/suite unit lokal.
